Reward architecture — revision 2

Multi-robot exploration: Isaac Sim & vision-based reward architecture

Extends the generic multi-robot reward design to run natively in Isaac Sim, treats an onboard camera + object detector as the only channel the policy actually perceives through, and trains the critic from Isaac Sim's privileged ground truth instead.

00What changed from the generic version

The previous design assumed the robot directly perceives a visited-grid crop and privileged teammate positions. Four things are different now:

  • Sim engine. The environment is built on Isaac Sim / Isaac Lab, which gives GPU-parallel physics, thousands of vectorized environments, and — for free — perfect ground-truth robot poses and occupancy.
  • Sensing. Each robot only has an onboard camera. What reaches the policy is a stream of detections: bbox=(x1,y1,x2,y2), size_px (area, width, height), label, confidence, stage2_conf. No privileged coordinates reach the actor.
  • Reward vs. perception split. Ground truth is still free during training — it now feeds the reward function and a centralized critic, while the deployed actor only ever consumes vision. This is a standard asymmetric actor-critic setup.
  • Tunable strategy space. A dedicated section maps reward/observation parameters to the emergent multi-robot behavior they produce — formation-keeping, territorial splitting, cautious vs. efficient obstacle clearance, and so on.

01Isaac Sim environment adaptation

Simulation & robot setup

Use Isaac Lab as the RL environment layer on top of Isaac Sim — its ManagerBasedRLEnv already separates observations, rewards, resets, and terminations into manager classes, which maps directly onto the module boundaries below. Each parallel environment instance is one exploration arena containing N robot Articulations, static obstacle prims, and a floor tagged with a walkable semantic class. Robots are tracked as a batched ArticulationView, so get_world_poses() returns a [num_envs, num_robots, 7] tensor — this is the ground-truth position source, and it costs nothing extra since the physics engine already computes it.

Occupancy / visited-grid ground truth

Keep the 70×70 visited grid as a GPU tensor, torch.zeros(num_envs, 70, 70), not a rendered sensor. Update it every step by projecting each robot's exact (x, y) plus vision radius into grid indices — pure tensor math, no rendering required, and it stays perfectly synchronized across thousands of parallel envs. The walkable mask can be pre-baked once per arena layout by rasterizing the USD stage's collision meshes, or pulled from Isaac Sim's occupancy-map extension.

Camera sensors

Attach one RTX Camera prim per robot, parented to its base link at the same mount point the real robot will eventually use — this parity is the actual sim-to-real contract, more so than any other part of the pipeline. For early development, attach a Replicator bounding_box_2d_tight annotator to that same camera: it gives a perfect, free detector so the reward/observation pipeline can be validated independently of detector noise. Swap it for a real trained detector's inference once the pipeline is confirmed working — same output schema, same downstream code.

Parallelization

RTX rendering, not physics, is the bottleneck for this setup, since it needs one camera per robot per environment. Isaac Lab's TiledCamera batches many low-resolution camera renders per GPU step. A common pattern: run physics at full rate, but run camera rendering + detector inference at a lower frequency (e.g. every 4th physics step), holding the last observation/action in between.

Domain randomization

Randomize lighting, obstacle materials, and camera sensor noise per episode via Replicator, so neither the detector nor the downstream policy overfits to one arena's rendering.

02Vision-based observation & detection encoding

Per robot, per step, the detector returns a variable-length list of detections with this schema:

stage2_conf implies a two-stage detector (propose → verify/classify). Treat it as a second gate: a detection should only count toward observation or reward if both confidence and stage2_conf clear their thresholds (see the tuning table).

Fixed-size encoding for a variable-length detection list

The actor needs a fixed-size input, but the detector returns anywhere from zero to many detections. Two options:

  • Set encoder (recommended). Pad or truncate to the top-K detections ranked by confidence × stage2_conf. Each row: [x1,y1,x2,y2 (normalized), area_norm, label_onehot, confidence, stage2_conf], passed through a small permutation-invariant encoder (per-detection MLP → max/mean pool, DeepSets-style). This keeps the policy indifferent to detection order and robust to K varying slightly.
  • Rasterized heatmap. Project detections onto a coarse image-plane grid (one channel per class, value = confidence). Simpler to fuse with a CNN if the visited grid is also fed as an image, but loses precise bbox geometry.

Recommended: the set encoder, with proprioception (own velocity, heading) concatenated after pooling.

Distance and bearing from bbox geometry

size_px is an inverse proxy for distance — a closer object produces a larger bbox. Since area scales roughly with 1/distance², use 1/sqrt(size_px) where a term needs to behave like a distance, rather than raw area, which is far too nonlinear at close range. The horizontal bbox center relative to image center gives bearing — useful for turn-toward/turn-away behavior.

Class-to-reward-term mapping

If the detector's class set includes teammate_robot, obstacle, and optionally a visual frontier marker, those three classes map directly onto the proximity, collision/margin, and frontier-shaping reward terms — computed from detected bbox geometry rather than privileged coordinates, whenever the goal is to make the actor's behavior itself reactive to what it visually confirms (as distinct from how the training reward itself is computed — see the next section).

03Reward: privileged ground truth vs. perception

This is the central architectural decision in the whole design: reward and observation are decoupled. Ground truth is free during Isaac Sim training, so reward should almost always be computed from the privileged state — exact positions, exact occupancy — even though the actor only ever sees camera detections. This keeps the reward signal clean and low-variance (not corrupted by detector false negatives or noise) while the policy itself only ever consumes the vision-based input that has to transfer to a real robot.

  • Exploration reward, overlap penalty, frontier shaping, collision penalties, time penalty — all computed from the ground-truth state manager, same formulas as the generic version.
  • Deliberate exception: if part of the goal is training the robot to react to what it actually notices (not just what's geometrically nearby), a detection-gated bonus/penalty can be computed directly from the vision stream. Use this narrowly — it means training reward now depends on a detector that may itself still be learning. See "vision-gated vs. ground-truth-gated" in the tuning table.
Rule of thumb: compute reward from privileged state by default; only switch a specific term to vision-gated when you explicitly want to shape active-sensing behavior (the robot learning to look toward what matters, not just react to it).

05Training the critic from ground truth

This is standard asymmetric actor-critic, same family as OpenAI's Dactyl / asymmetric self-play work — the refinement here is exactly what goes into each network's input:

  • Actor input: the vision-based observation from Section 2 — detection set encoding + proprioception. Identical network, shared weights, run per robot. This is the only thing that has to be plausible on a real robot.
  • Critic input: the full privileged joint state — every robot's exact pose and velocity, the complete 70×70 visited grid (not just a local crop), the full obstacle map, and ground-truth pairwise distances. One centralized critic can see everyone, precisely because it never has to run outside simulation.

Advantages are computed from the privileged critic's value estimates; the policy-gradient update is applied only to the vision-conditioned actor. In Isaac Lab terms: define two observation groups in the same ObservationManager — "policy" (vision + proprioception) and "critic" (privileged state). Most Isaac Lab RL wrappers (RSL-RL, rl_games, skrl) already support this asymmetric split natively.

Watch for: a policy that appears to work in sim because the reward — computed from privileged state — happens to correlate with a fixed obstacle layout the detector alone couldn't have inferred. Randomize the arena layout per episode so training reward can't leak privileged information into the deployed policy through the back door of environment determinism.

06Tunable parameters → emergent strategies

Every row below is a knob on the reward or observation pipeline; the right column is the qualitative multi-robot behavior it tends to produce. These interact — treat this as a starting map, not independent dials.

ParameterHigher value →Lower / negative value →Notes & tradeoffs
proximity_reward_w tight flocking — robots stay within detection range of teammates, effectively keeping formation robots spread apart to maximize independent coverage too high collapses exploration efficiency into clustering; pair with overlap penalty to prevent full collapse
overlap_penalty_w strict territorial division emerges — implicit Voronoi-style split of the map redundant, overlapping coverage — slower but more robust to a robot dropping out tune with frontier_reassign_freq; too strict + too infrequent reassignment causes thrash at boundaries
obstacle_margin wide, cautious berths around obstacles — slower but safer paths, better real-world transfer tight paths hugging obstacles — efficient in sim, riskier on real hardware with detector/pose error use a continuous penalty ∝ 1/distance² for smooth avoidance; a binary collision-only penalty gives no shaping and tends to produce wall-hugging loops
time_penalty urgency — faster, more direct paths, more willing to cut close to risk slower, more thorough and cautious exploration interacts strongly with obstacle_margin — high urgency + tight margins is the most collision-prone combination
frontier_shaping_w goal-directed beelining toward the nearest unclaimed region locally greedy — thorough nearby coverage, slower macro progress, prone to dead-end wandering late in an episode this is the fix for the sparse-reward "90% explored, target is far away" problem from the base design
team_bonus_w vs individual_w higher team weight: cooperative, will sacrifice individual efficiency for team completion higher individual weight: risk of free-riding, or competitive/territorial behavior start near 0.3 team / 0.7 individual and move only if you observe under-cooperation, not before
detection_range longer reliable teammate detection range: earlier coordination, loose but well-timed territory splitting shorter range: independent, greedy behavior — robots only react to teammates once very close this is effectively the camera FOV / max reliable detection distance, a hardware-grounded parameter, not a free one
min_safe_distance larger: spread-out swarm, wide berth kept around teammates at all times smaller: allows tight clustering or convoy-style following sets the floor for how close proximity_reward_w is even allowed to pull robots together
conf_threshold / stage2_conf_threshold higher: reacts only to confident detections — safer, but slower to react, can miss real but low-confidence hazards lower: jumpy, reactive behavior; false positives inject reward noise and destabilize training tune stage2_conf_threshold slightly looser than confidence_threshold if stage-2 is a verifier, not a duplicate detector
bbox_size→reward curve reward ∝ size_px: "get closer" — approach/inspect behavior reward ∝ 1/size_px: "stay small in frame" — avoidance / wide-FOV coverage behavior a third shape, reward ∝ −|size_px − target|, produces station-keeping / fixed follow-distance escort behavior instead of either extreme
frontier_reassign_freq reassign every step: tighter, near-optimal territory split, more compute reassign every K steps: cheaper, but a robot can briefly "poach" a teammate's frontier before correction every 5–10 steps is a reasonable starting point for a 70×70 grid
vision-gated vs ground-truth-gated reward vision-gated: the policy must actually look toward teammates/obstacles to get credit ground-truth-gated: reward available regardless of where the camera points vision-gated produces active-sensing/scanning behavior but couples reward quality to current detector quality — see Section 3's callout

07Module skeleton

  • IsaacSimEnvWrapper — vectorized ManagerBasedRLEnv subclass; owns the parallel arenas and robot Articulations
  • GroundTruthStateManager — privileged; GPU-tensor visited grid, exact poses, occupancy, obstacle map, pairwise distances
  • CameraDetectionPipeline — per-robot RTX camera + detector inference (Replicator bbox annotator during bootstrap, trained detector after)
  • DetectionEncoder — set encoder: variable-length detections → fixed-size actor observation
  • RewardComponents — pure functions sourced from GroundTruthStateManager: exploration_reward, overlap_penalty, frontier_shaping_reward, collision_penalty, time_penalty, plus optional vision-gated variants
  • TeamModule — completion check, shared team bonus, triggers the global reset broadcast
  • RewardAggregator — weighted sum per robot
  • ActorNetwork — vision + proprioception in, action out; shared weights across robots; the only network that deploys
  • CriticNetwork — privileged joint state in, value out; centralized; training-only, discarded at deployment

08Per-step execution order

1. Actor(vision_obs) -> actions for all robots, batched across envs
2. Physics step in Isaac Sim
3. Render RTX camera frames per robot -> detector inference
   (or pull Replicator ground-truth bboxes during the bootstrap phase)
4. GroundTruthStateManager update: exact poses -> visited grid, occupancy
   (independent of anything vision produced this step)
5. RewardComponents computed from GroundTruthStateManager
   (+ any deliberately vision-gated terms, using this step's detections)
6. TeamModule.check_and_bonus()
   -> on completion: reset visited grid + recently-visited buffer
      + frontier assignment, together, in the same step
7. RewardAggregator -> scalar reward per robot
8. DetectionEncoder(detections) -> next actor observation
   GroundTruthStateManager        -> next critic observation
9. Store (actor_obs, critic_obs, action, reward) transition for the
   PPO / MAPPO update

09Implementation notes

  • Bootstrap with ground truth first. Validate the reward architecture using the Replicator bbox annotator before swapping in a real trained detector — this separates "does the reward design work" from "is the detector any good" as two independently debuggable questions.
  • Decouple physics-Hz from perception-Hz. If detector inference can't keep pace with physics across hundreds of parallel envs, run vision + policy at a lower frequency and hold the last action between ticks.
  • Randomize arena layouts per episode to prevent the reward function's privileged information from leaking into the deployed policy through memorized, deterministic layouts.
  • Keep the reward/perception boundary explicit in code — two clearly separate manager classes. It's the easiest architectural line to blur once ground truth and vision live in the same step loop.
